## ۴. معماری مختصر
Next.js 16 + TypeScript (web) · worker مستقل Node (صف یادآوری، sync تقویم، پاکسازی) · PostgreSQL 16 + Prisma 7 · Docker Compose پشت Traefik موجود سرور. جزئیات: `docs/ARCHITECTURE.md`.
تصمیم‌های مهم: صف مبتنی بر جدول با `FOR UPDATE SKIP LOCKED` به جای Redis؛ نوبت‌های تکرار «مجازی» با رکورد فقط برای استثناها؛ تاریخ بدون ساعت به صورت تاریخ محلی + نوع تقویم جدا (هیچ قاعدهٔ شمسی به timestamp تقلیل نمی‌یابد)؛ برنامه‌ریز قانون‌محور و توضیح‌پذیر، AI فقط برای فهم متن و همیشه با پیش‌نمایش؛ شناسهٔ قطعی رویداد گوگل برای جلوگیری از تکرار.

## ۶. شواهد موبایل، PWA و HTTPS
- اسکرین‌شات‌های e2e (موبایل و دسکتاپ) در artifact «e2e-results» اجرای CI موجود است؛ بررسی دستی ۳۷۵px در حالت روشن و تیره انجام شد.
- production: `isSecureContext=true`، service worker فعال با scope ریشه، manifest با `display: standalone` و آیکن‌های ۱۹۲/۵۱۲/maskable، `PushManager` موجود.
- مسیر به‌روزرسانی واقعاً آزموده شد: پس از استقرار نسخهٔ جدید، بنر «نسخهٔ جدید» ظاهر شد، با لمس آن صفحه بازخوانی و cache نسخهٔ قبل حذف شد.
- HTTP→HTTPS با ۳۰۱، HSTS، `X-Frame-Options: DENY`، `nosniff`. پورت ۵۴۳۲ از بیرون بسته است.

## ۸. دستورها
```bash
cd ~/apps/hamrooz/current && DC="docker compose -p hamrooz -f deploy/compose.yml --env-file release.env"
$DC ps                                   # وضعیت
$DC logs -f --tail 100 web               # لاگ (worker/backup/db)
$DC restart web worker                   # restart
~/apps/hamrooz/ops/deploy.sh <sha>       # دیپلوی (با backup پیش از migration)
~/apps/hamrooz/ops/rollback.sh [release] # rollback اپ (migration برنمی‌گردد)
~/apps/hamrooz/ops/restore-test.sh       # آزمایش restore در کانتینر جدا بدون شبکه
~/apps/hamrooz/ops/restore.sh <dump>     # restore واقعی (مخرب، با تأیید)
```
backup روزانه با نگهداری ۱۴ روز؛ restore-test روی آخرین backup موفق بود (owner بازیابی شد). rollback به نسخهٔ قبل و برگشت به نسخهٔ جاری روی production آزموده شد.

## ۹. تنظیمات باقی‌مانده برای مالک
1. **ورود اولیه**: حساب مالک `takner@gmail.com` با رمز تصادفی ساخته شده است. رمز در `~/apps/hamrooz/private/owner-credentials.txt` (مجوز ۶۰۰) است؛ بعد از ورود از «تنظیمات ← حساب» رمز را عوض و فایل را حذف کنید. (هویت مالک از ایمیل حساب کاربر برداشت شد؛ اگر ایمیل دیگری مدنظر است `OWNER_EMAIL` و حساب باید عوض شوند.)
2. **Google OAuth**: پروژه در Google Cloud، فعال‌سازی Calendar API، OAuth client از نوع Web با redirect `https://auto.levian.tech/api/google/callback`، قرار دادن `GOOGLE_CLIENT_ID/SECRET` در `shared/app.env` و `$DC up -d web worker`. اگر consent screen در حالت Testing بماند، refresh token گوگل هر ۷ روز منقضی می‌شود؛ برای استفادهٔ دائمی باید Publish شود.
3. **صوت**: `OPENAI_API_KEY` (و اختیاری `ANTHROPIC_API_KEY` برای برداشت هوشمند).
4. **آزمایش‌های کوتاه مالک** (چون دستگاه/حساب واقعی در اختیار من نبود):
   - اعلان: روی اندروید با Chrome، یا آیفون (iOS ≥ ۱۶٫۴) پس از «Add to Home Screen» ← تنظیمات ← اعلان‌ها ← «فعال‌سازی» ← «ارسال اعلان آزمایشی». سپس یک کار با یادآوری ۲–۳ دقیقهٔ بعد بسازید و برنامه را ببندید.
   - تقویم: اتصال، انتخاب تقویم، «همگام‌سازی الان»، دیدن قرار در امروز، «ارسال به Google Calendar» برای یک کار و دوباره زدن آن (نباید رویداد دوم ساخته شود).
   - صوت: جملهٔ «بیمه ماشین دوازده آبان تموم می‌شه؛ یه هفته قبل و روز قبل یادم بنداز» را ضبط کنید.

## ۱۰. مشکلات شناخته‌شده و ریسک‌ها
- backup فقط روی همان سرور است؛ **کپی خارج از سرور تنظیم نشده**.
- push، تقویم و صوت با سرویس/دستگاه واقعی تأیید نشده‌اند؛ کیفیت STT فارسی سنجیده نشده.
- rate limit درون‌حافظه است (با restart صفر می‌شود؛ برای تک‌نمونه کافی است).
- sync تقویم پنجره‌ای (۱ روز قبل تا ۳۰ روز بعد، هر ۱۵ دقیقه) است، نه sync token/webhook.
- برنامه‌ریز کار را تکه نمی‌کند؛ کار شخصی در ساعت کاری قرار نمی‌گیرد مگر موعدش رسیده باشد؛ نوبت‌های جامانده‌ی کار تکراری خودکار برنامه‌ریزی نمی‌شوند (تصمیم با کاربر).
- Content-Security-Policy تنظیم نشده (سایر هدرهای امنیتی هستند).
- `npm audit`: ۴ مورد high در وابستگی‌های transitive خود Prisma CLI (`mysql2`، `deepmerge-ts`)؛ CLI فقط هنگام migration با ورودی مورد اعتماد اجرا می‌شود و runtime از آن استفاده نمی‌کند. راه‌حل پیشنهادی npm تنزل به Prisma 6 است که اعمال نشد؛ با انتشار نسخهٔ اصلاح‌شدهٔ Prisma به‌روزرسانی شود.
- rollback دیتابیس تضمین نمی‌شود؛ فقط از طریق restore پشتیبان پیش از migration.
- هشدار خارجی (alerting) وجود ندارد؛ فقط `/api/health` و healthcheck کانتینرها.
- یک دیتابیس توسعه (`hamrooz-devdb`، فقط روی 127.0.0.1:5441 سرور) برای تست‌های محلی ساخته شد؛ برای حذف: `docker rm -f hamrooz-devdb`.
